# Changelog

All notable changes to this project are documented here. The format follows
[Keep a Changelog](https://keepachangelog.com/) and the project adheres to
[Semantic Versioning](https://semver.org/): MAJOR.MINOR.PATCH, where MINOR
adds tools/capabilities and PATCH fixes. The server reports its version in
the MCP `initialize` response (`serverInfo.version`).

## [Unreleased]

### Added

- `delphi_db`: the databases the operator gives a workspace, used by NAME and through operations - the agent never writes SQL. The operator defines them in the server's connections file (`connections\databases\db-connections.json`, next to `settings.ini` and outside every root: projects, each with its databases - server, database, user, password, port, engine, readonly) and opens projects to a workspace with `DbAllowedProjects=` in its section of `settings.ini` (`*` = all); without one, `delphi_db` is not in `tools/list` and a call answers `DB-002`. `command=connections` lists the databases of the workspace as `project/alias` - the name every command takes - with their engine (the FireDAC driver) and whether they are read-only; the ones declared wrong come under `unusable` with why (`DB-001`, `DB-005`). The agent never sees the server, the real database or the credentials. The engines are the FireDAC drivers the server links (MSSQL and PostgreSQL); a driver that needs a client library loads it from `drivers\<DriverID>\` of the server, never from anywhere else. The budget of `tools/list` rises to 110,000 characters for the new tools.

### Fixed

- `delphi_config remove-deployfile` takes the entry as the project lists it, even one that points outside the workspace, as `remove-unit`, `remove-searchpath` and `remove-project` already did: a `DeployFile` that a project copied from another machine names on that machine's disk was refused with `GUARD-002`, and the `.dproj` - which only `delphi_config` writes - kept it, so `delphi_build` kept refusing the project with `BUILD-050` (found by an agent, 6-nov). The entry goes from the `.dproj` and the `.deployproj`, and the file it names is never opened. `BUILD-050` now says that `remove-deployfile` removes a file to ship.

## [1.28.0] - 2026-11-06

A minor version that closes the list the project kept open. `delphi_desktop` drives a Linux
target with KDE Plasma - its hands through the desktop portal, the overview and the scale
asked of the desktop - and gains `drag`, which moves and resizes windows on Linux and on
Windows. Creating a unit is `delphi_create`'s alone (`delphi_edit` no longer has
`createunit`), `tools/list` announces `delphi_adb` and `delphi_desktop` only where the
workspace declares somewhere for them to go, and the MCP `instructions` start with a short
map of the tools. An edit no longer writes a text form the IDE's parser would stop reading
(`DSGN-124`), a long written block is echoed head and tail, and a rename asks each project's
engine about a namesake in another project. A review of the landscape of the whole source,
before the release, fixed eleven things that failed - among them the vault's governance
files and the device names, now judged as Windows names them whatever the server's locale.
No setting needs to change; deploy the server with its two form renderers (they speak
protocol 8). Validated before the release through Hermes on a second machine by Qwen3.8
Flash Next (directed tests of what changed, three rounds, and a full test of every tool);
what the review of the whole source found after those tests was fixed and measured here.

### Added

- `delphi_desktop` on a Linux target with KDE Plasma. The hands (`tap`, `type`, `key`, `overview`) go through the standard remote desktop portal where the desktop does not offer GNOME's own interface, which keeps its path: the node chooses by what the session bus offers, not by a list of desktops. The first time on a machine the desktop asks the operator once - accept it, ticking that it should not ask again - and the node keeps that permission for the target's user, outside the folder every deploy rewrites (`~/.local/state/mcp-desktop-node`); later sessions do not ask (measured on Fedora 44 with Plasma 6.8: the first answer took the operator 14.7 s, the next ones 13 ms). If nobody accepts it within 40 s the answer says what to ask the operator for. Where the desktop does not say its scale, the node measures it: the screenshot's width over the logical screen's (`NODE-047`; 1.25 at 125%, measured). `overview` asks KWin for its Overview action by name, chosen by what the bus offers (`NODE-050`): on Plasma, Super opens the application launcher, not the overview (measured), and the key of the action is the user's to change; its note (`DESK-008`) no longer describes GNOME's overview only (Plasma draws the windows under a row of virtual desktops). The whole tool was tested on Fedora 44 with Plasma 6.8 and with GNOME.
- `delphi_desktop command=drag`: press at `x,y`, move to `tox,toy` and release, like a hand - a window's title bar moves it, and pressed 3 pixels past the right or bottom edge of its `windows` rectangle it resizes it (a press inside the window goes to the application: the description says where to press); also a slider, a selection or a drag and drop inside an app. Both points are measured on the same screenshot and one `frame` converts them; the node checks the destination before it presses and always releases the button (`NODE-048`, `DESK-026`). Moving a window had no gesture of its own: on KDE Plasma it took four (its window menu and a click), and its keyboard shortcut is not assigned by default (measured). Measured on Fedora 44 with Plasma 6.8: a title bar dragged by (+200, +93) moved the window exactly that much, and a left edge dragged to x=100 left it at 101; a right edge resizes when pressed from its first pixel outside to 10 pixels out, and at 20 it does nothing (the press lands on the desktop); on GNOME the same, and a maximized window dragged by its title bar unmaximizes and follows; on Windows 11 an Explorer window dragged by (+359, +194) moved exactly that much, and back.

### Changed

- The MCP `instructions` of `initialize` now start with a short map of the tools - where to start (`delphi_workspace`, `delphi_help`), what to read, edit, build and test with - for the clients that load a tool's schema only when they ask for it and see little more than names; the vault's protocol, where there is one, comes after it. About 450 characters, which travel in every prompt.

- Creating a unit is `delphi_create`'s alone: `delphi_edit` no longer has `createunit` (nor its `content` and `eol`), and `delphi_create` takes `eol` (`crlf`, the default, or `lf`) for a unit and an include - the one thing only `createunit` did. Its answer for a unit or an include now says the encoding the file was born in, read back from disk with `delphi_read`'s label, and its line endings, as `createunit` did. Measured before removing it, with Qwen3.8 Flash Next on this server's own tool definitions: asked to create a unit, it chose `delphi_create` 12 times out of 12 with `createunit` offered and 12 out of 12 without it; in Hermes' history, 38 `createunit` calls against 257 `delphi_create kind=unit`. It was the same rules through a second door - a valid name, a content that matches it, never overwriting - and about 600 characters of every `tools/list`. A client that still sends it gets `SYS-015` with the parameters `delphi_edit` takes.

- `tools/list` announces `delphi_adb` and `delphi_desktop` only where the workspace declares somewhere for them to go - a device in `AdbAllowedDevices`, a host in `DesktopAllowedHosts` or `DesktopViewHosts`. Without one every call was refused anyway, and the two were about 10 KB of every `tools/list` (measured in 1.27: the size grew, not the count, and the clients that load the whole list pay it in context). Like the vault tools: they stay callable, the call says what is missing, and `delphi_help` (`tasks`, and `command=tool` for either) says they are not announced and which key opens them. The documentation still lists all 42.

- `delphi_edit`, its batches (`edits`) and `delphi_changeset` no longer write a text form (`.dfm`, `.fmx`) that the IDE's form parser read before the change and would not read after it: they answer `DSGN-124` and nothing is written, as `delphi_designer` and `delphi_styles` already did. They wrote it and warned afterwards with `DSGN-123` (a `//` comment in a `.fmx`: the IDE does not open the form and the program does not load it). A batch or a changeset is judged on what it leaves, not step by step: a step that does not read yet and a later one that fixes it are written; a changeset that would leave one goes back whole (`CHSET-026` with the cause). A form that was ALREADY unreadable is still written, with its `DSGN-123`: fixing one by hand takes steps that do not read yet. The parser runs in the server, so judging before writing costs what judging afterwards did.

- `delphi_rename_symbol` no longer refuses a rename for a namesake in ANOTHER project that the engine of that project resolves to another definition. Two projects with default names, the second in a subfolder of the first, left not applicable with `RENAME-017` every rename in the first of a name the second also declares (its `FormMain`: found by Hermes' full test of 1.27.0): the engine of the renamed symbol's project resolved the other project's lines with settings that are not theirs, and a namesake read that way may be the very symbol. Each such line is now asked to the engine of its own project - the project the server gives that file, as every tool does: when it says another definition, the line stays as it is and the rename only warns (`RENAME-024`); when it says the renamed symbol, it is a reference and is renamed with the rest. That second case is the one from the field, where a sibling project's call was taken for a namesake and the rename broke its build: measured with a call that the first project's engine resolved to a unit of its own with the same name, and the call's project - what dcc compiles - to the renamed symbol. And the reverse, measured on the way: a call in a sibling project that compiles its OWN copy of the unit was confirmed by the first project's engine, and the rename would have renamed it and broken that project; now its own engine says it is another symbol, and it stays. Every line of another project, confirmed or not, is judged this way - but not a line of a unit that the renamed symbol's project lists too (a shared unit both name by its path): it is a line of that project as well, the engine that asked judges it and no other engine is started for it; one whose own engine cannot be asked (it does not start, or the bound of files to open is reached) is not confirmed: it goes to `unverified` with `LSP-054`, and the rename refuses (`RENAME-018`). `delphi_references` gives each line judged by its own project its `project`, and `rejectedByTheirProject` counts the namesakes. A namesake in the SAME project, or in no project, still refuses with `RENAME-017`: it has one judge only.

- `delphi_paserver` reads the fields of a connection profile through one reader in every command - the profile the IDE lists, from its file, through the IDE's door. `add-profile` (the duplicate host check, and the encrypted password for the IDE's seat), `get-sdk` and `reseat` each read it by hand, each with its own failure. `get-sdk` with a profile that cannot be read now answers `PAS-054`, as the host gate already did for that profile, instead of an internal error.

- The echo of `delphi_edit` and `delphi_textedit` - the lines read back from disk after a write - no longer repeats a long written block whole: up to 40 lines it is whole, as before; a longer one gives its first 15 lines and its last 5, and between them how many are not repeated and the `delphi_read` call that shows them. The audit line still covers the whole file. Replacing 323 lines of a unit answered with 457 lines, 16,798 characters, for an entry of 14,528 (an agent's report, 6-nov); a batch (`edits`) already gave one line per entry. One rule for the two tools.

### Fixed

- `delphi_edit` called with `createunit`, `content` or `eol` - the unit creation it no longer has since this version - says where it went (`EDIT-132`: `delphi_create kind=unit`, with `content` and `eol`), instead of the generic unknown-parameter refusal that only listed the parameters it takes. A client that keeps an older tool list still offers them: Hermes' did, in the three rounds of its test of this version. The retired parameters are one table at the call's gate, which also holds `delphi_git`'s `args` (`GIT-068`).

- `delphi_designer set` says what else the IDE's writer changed in the component when it stored the property: `alsoWritten` (the lines it wrote or changed) and `alsoRemoved` (the ones it took out), with `DSGN-189`. Setting a `TextSettings` value of an FMX label also writes `StyledSettings` without that flag - it decides which of the label's text settings show - and the answer said only the line of what was set; Hermes found it only through a `get`, in two rounds of the 1.28 test. Both doors of `set`, one property and several (`props`).

- A derived file that already says exactly what would be placed is no longer rewritten, and no copy of it is sealed in the trash: a `.bin.style` or `.res` of `delphi_styles build`, and what `out=` places for a preview, a capture or a logcat. Every repeated build sealed an identical copy of each derived file (measured: the same SHA-256, one more copy per build); the rule was already the one of every other writer (a file written whole that says the same is left as it is).

- `delphi_paserver remote-run` took `job` and did nothing with it: only `kill` and `output` read a job, and an agent that passed one to `remote-run` believed it had. It now answers `PAS-051`, which says the commands `job` goes with, as every other parameter that does not belong to its command.

- `delphi_config add-unit` and `remove-unit` with a `path` that is not a `.pas` say what `path` takes: the unit's `.pas` file, extension included - for a unit already in the project, also as `view section=units` lists its `file`. `CFG-036` said only that it was not a `.pas` unit, and an agent that gave `remove-unit` the unit's name, as that same `view` lists it under `unit`, lost a turn finding out (Hermes' full test of this version).

- The vault's governance files (`AGENTS-VAULT.md`, `AGENTS-VAULT-WRITE.md`, `MEMORY.md`, `VAULT-INSTRUCTIONS.md`) are recognised as Windows names them, whatever the server's locale. They were compared with the user's locale, and on a Turkish or Azeri Windows `vault-instructions.md` was not `VAULT-INSTRUCTIONS.md` for the judge while the disk took it as that file: `vault_create` could write the instructions every client of the workspace receives. The device names a path may not use (`CON`, `CONIN$`...) are compared the same way.

- `delphi_edit insert=metodo` of a generic method that already has its implementation (`procedure TFoo.Bar<T>(X: T)`) refuses it as an existing method, instead of writing a second implementation (`E2004` at the next build) and answering that only the implementation was written.

- `delphi_designer preview` no longer counts in `DSGN-114` ("the form will fail to open until they are fixed... set them or remove them") what the form's own classes publish - the note beside it, `DSGN-152`, says that is not an error of the form - nor what an object of a substituted (not installed) class had skipped, which `lint` already left out. One judge for both now.

- `delphi_designer delete` takes the server's write lock only to re-read and to write, as `set` and `insert` do. It held it for the whole command, and a name that is not in the form's text asks the IDE's form reader (an inherited component), so every write of the server waited while the helper loaded the design packages, without the client's deadline.

- `delphi_config set-property` with a macro in the value (`.\$(Platform)\bin`) no longer warns that "msbuild reads ... instead": it compared the value written with the one msbuild reads, already expanded. It now asks whether the element it wrote is the one that wins, and still says so when a later group overrides it.

- A form whose class is not `T` + its name (`{FormMain}` of class `TBaseForm`) is found by the class its designer declares: `delphi_create ancestor=TBaseForm` answered `CREATE-038`, and neither `insert` (a frame) nor `preview` (an ancestor in another folder) found it either. The name is tried first, as before; the root of the designer decides.

- A `DCCReference` written with another spelling of the same path (`.\UMain.pas` for the `.dpr`'s `'UMain.pas'`) is the unit's: `delphi_config view` showed `dproj:false`, `remove-unit` left it behind and `add-unit` added a second one. Both are resolved from their files and compared as the same file.

- `delphi_create kind=include` with a `project` that is not a project refuses it (`CFG-033`), as `kind=unit` and the forms do; it created the include and said nothing.

- `delphi_desktop type` with a line break says that it writes one line and how to press Enter between two (`DESK-027`), before doing anything; it answered `RUN-026` about an "Argument 3" the agent never sent. And the text is typed as given: the blanks around it are no longer trimmed.

- `delphi_paserver get-sdk active=` takes a yes or a no with the server's one grammar (`yes`/`no`, `true`/`false`, `1`/`0`, `on`/`off`) and refuses anything else with `PAS-073` before doing anything. `active=on` was taken as no, and so was any other word.

- A write that fails half way (a full disk) no longer leaves its temporary file next to the file it was replacing. One of the two places that wrote one removed it and the other - the writer of almost every file in the workspace - did not.

- `delphi_desktop` on a Windows target reached through a remote desktop session says what to ask the operator for when a gesture does not get through. With the session's remote desktop window minimized on the operator's machine, or the session disconnected, Windows takes no input (0 of N, access denied) and refuses the screen copy (the capture still comes, window by window); the refusal (`NODE-011`) said only that, and the next try met the same wall. It now says which of the two it is and what to ask for: restore that window (it may stay behind others: visible without focus, the session takes input - measured) or reconnect the session; for a minimized one it also names the client setting that keeps it drawn (`RemoteDesktop_SuppressWhenMinimized` = 2 on the machine whose window it is: measured, with it a minimized session takes input and the screen copy, and without it neither). Disconnected is asked to Windows (the session's connection state), not guessed from the input desktop, which a locked session refuses too; `status` shows it in its STATE line. Measured on Windows 11 24H2 with the operator's remote desktop window maximized, unfocused, minimized and disconnected.

- `delphi_edit removeuses` with several units that sit next to each other in the clause no longer leaves their comments behind. A `//` after an entry's comma belongs to that entry and goes with it, and so it did for one unit; with two or three neighbours removed in one call, the comment of every one but the last stayed in the clause on a line of its own, and when the removed ones were the last of the clause, the first one's comment could end up on the line of the entry that now closes it (`UB; // de UC`). The same holds for `removeuses` in a `.dpr`. The clause echoed in the answer of `adduses` and `removeuses` now shows the `//` that the last entry keeps after the `;`: the copy stopped at the `;`, and a comment still in the file looked lost. And a note on a line of its own above the removed unit stays, as it always did - it may be about what follows -, but when that unit was the LAST of the clause the note went up behind the `;` of the entry that now closes it (`UA; // note about UB`) and read as that entry's comment; it now stays on its own line, in a `.pas` and in a `.dpr`.

- `delphi_designer set` (and `insert` with `props`) no longer blames a form's component for what the IDE's form reader said about a component of the SAME NAME in another file - an inline frame's own file, or an ancestor. With an ancestor whose `Edit1` holds a value the reader does not load, `set Edit1.FontColor=claRed` on the inherited form was refused with `DSGN-149` ("the reader does not load that value"), when what does not load is the ancestor's: it is now written, and `readerNote` (`DSGN-159`) says it could not be judged because the form did not load before either. With an inline frame in that state, the same `set` on the form's own `Edit1` wrote two lines - the one the IDE's writer stores (`TextSettings.FontColor = claRed`) and the given one besides -; now only the first. The reader says which file it was reading, and only what it said reading THIS form is this form's (measured on 5-nov with both shapes).

- `delphi_designer set` of a property a class reads but never writes by that name - in FMX, `Font.Size`, `Font.Family` or `FontColor` on a `TLabel` or a `TEdit`, kept for old forms and stored by the IDE in `TextSettings` - answered `notStored` (`DSGN-165`: "it is the value the class already gives it") while it wrote `TextSettings.Font.Size = 20`. It now answers `storedIn` with what the IDE wrote. Which properties those are is asked of the class itself: what its `DefineProperties` declares with no writer (protocol 8 of the form renderers: the server and its renderers go together). And a property never stored by its name for which the IDE writes nothing now says `notStored` instead of an empty `storedIn`.

- A program the server runs by its path - git, msbuild, adb, paclient, brcc32, `DelphiLSP.exe` - is no longer taken from a folder that the agent of ANOTHER workspace can write. The judge of "the operator's program, where no agent writes" asked only the calling session's jail: with a folder of the service's PATH inside workspace B's root, a `git.exe` left there ran with the service's account when workspace A's agent called `delphi_git` (measured with an inert probe). A program inside the write root of any declared workspace, or of the local launch, is now nobody's operator program, for every session: `GIT-050` and its siblings say so, as they already did for the calling agent's own roots.

- `delphi_paserver add-profile` refuses a platform that only LOOKS like one of paclient's (`Linu` + U+02E3 + `64`, a superscript x) instead of creating the profile with the default platform. The gate compared with the user's locale, which takes 6 to 15 such characters per platform name for the letter they resemble (measured with Windows' own comparison); `add-profile` looked the platform up ordinally, did not find it and fell back to the default. Both now ask one judge, which folds only ASCII letters.

- `delphi_changeset commit` no longer says that every file it touched has its backup in `__delphi-patch`: a move is a rename and keeps its content without a copy, and a created file had nothing before it. It now says which ones do. And `delphi_config view` no longer calls a version key written twice in the same group "written for other platforms or configurations": it says that the key may be written twice, and that the build takes the first one (measured on the binary).

- `delphi_delete` of an EMPTY folder no longer answers that it cannot be removed when something holds it for an instant (the indexer, an antivirus, a process that just let go of it): removing an empty folder now takes the retries a rename already took - five tries 100 ms apart, only for the codes a passing reader gives (5, 32, 33). One place had them (the folders a failed clone leaves) and six did not: that delete, the move that merges a folder into an existing one, the tree remover, the trash folders a purge leaves empty, and the empty folder paclient leaves among the IDE's SDKs. Now they share one helper.

- The engine of a project sees the units its main source lists by `in '...'` as they are NOW. DelphiLSP fixes which file each unit of a project is when it loads the project, and never looks again - measured with the engine alone: not with the same settings given again, nor with settings that change, nor with a file-change notice for the .dpr, nor with the .dpr open as a document; only a new engine sees it. After `delphi_config remove-unit` and `add-unit` moved a unit to another file (`UCalc in '..\UCalc.pas'` to the copy beside the project), `delphi_definition`, `delphi_references` and the judgment of `delphi_rename_symbol` answered with the old file until the server restarted. The server now notes what the main source lists when an engine starts and, when that changes, starts another for the next request; a change of the .dpr that leaves that list as it was (a comment, the body) keeps the engine, and one with a request in flight is replaced on the next one.

- `delphi_designer set` (and `insert` with `props`) on FMX now does what the IDE does when a property is changed in the Object Inspector. `TextSettings.Font.Size=24`, bold or `FontColor=claRed` on a label answered OK, wrote the lines and changed nothing on screen: the value stayed in `StyledSettings`, so the style won (measured on a new form: the preview drew it small and black). FMX takes a changed setting out of `StyledSettings` only when it is changed on the LOADED component, not while the form is read (`TTextSettingsInfo.DoTextChanged`, measured), and the agent's value was read with the form. It is now applied on the loaded form, as the Inspector does, and then the IDE's writer stores it - `StyledSettings` included - so the class does its own work and no list of properties stands in for it. Values that are text or a block (a string, a collection, binary data) are still read with the form, and if the renderer cannot set one the judge runs the way it did. The renderers' protocol goes to 6.

- `delphi_designer layout` (and `insert`, `set parent=`) on an FMX form says what is DRAWN of a control that sticks out of its parent. The warning said, for every one, that FMX draws that part over what is around it "unless a container clips its children (ClipChildren)" - right for a container that does not clip, wrong for one that does, and for what sticks out of the form (found by Hermes' directed test of 1.27: a warning said "not visible" while the preview drew it whole). The renderer now works out, on the live controls, what FMX paints of each one - the rule of FMX's own painting: every container that clips its children cuts by its own `ClipRect`, and the form by its area (`AbsoluteClipRect`); not `UpdateRect`, which is what FMX repaints and which a shape widens by its stroke (measured: one pixel more) - and the warning says one of three things: nothing clips it and it is drawn over what is around it; only `(x1,y1)-(x2,y2)` of it is drawn; or none of it is. No list of classes decides who clips. The renderers' protocol goes to 7: the VM gets the server and its renderers together.

- `delphi_desktop`'s `windows` on Linux no longer lists a window that is fully transparent. On KDE Plasma, Xwayland's video bridge (`xwaylandvideobridge`) showed as an 800x450 window in the middle of the screen where the capture showed nothing (found by Hermes' test of Plasma; measured on Fedora 44 with Plasma 6.8). The node reads what the window declares in `_NET_WM_WINDOW_OPACITY`, which the compositor applies, as it already left out the windows Windows cloaks.

- `delphi_desktop`'s `code` names the evdev codes of Backspace (14) and Delete (111): an agent pressed 127, which is Compose, believing it was Delete (Hermes' test of Plasma).

- A page of a list no longer shrinks in silence when it is asked for more than it holds. `maxresults=5000` in `delphi_list` or `delphi_search` brought 500 with no word of why (found by Hermes' full test of 1.27.0); the page now says it in `pageNote` (`LIST-017`: the most a page holds here, and what was asked), and `vault_search` under its header - only when the cap is what cut it, not when the rest fits. One place for every paged list (`delphi_list` files and folders, `delphi_search`, `delphi_projects`, `vault_search`, `delphi_docs search`).

- `delphi_styles set`'s `STYLE-059` no longer blames the class for a value the FILE gives. `Width = 120` on an object whose file already says `Size.Width = 120` answered "the value its class already gives" (found by Hermes' full test of 1.27.0); FMX's own writer leaves the object as the file already leaves it, and that is what it says now - its class's value (its default, a clamp, an Align) or one the file already holds in other properties - and that nothing was written and no backup was taken. The two cases give the same written object: the answer says what that judge measures, not a list of names that would tell them apart.

- `delphi_paserver test-connection` with a profile that does not connect says why. It answered `connected:false` and paclient's output with no code and no advice (found by Hermes with a target switched off); the server now measures the TCP route to the profile's own host and port, as `test-connection` without a profile does, and answers `PAS-028` (no route: what to check, in order) or `PAS-072` (the route is there: what refused is the PAServer or the profile, and `paclientOutput` says what), with `tcpReachable`, `host` and `port`. paclient alone cannot tell them apart: with the port closed and with the port open and no PAServer behind it, it prints the same `E0003` (measured).

- `delphi_desktop`'s `windows` gives the VISIBLE rectangle of a window that draws its own frame - a GTK application with client-side decorations, every FMX application on GNOME -, and `screenshot window=` crops to it. Its X11 window carries the shadow inside, invisible: the rectangle came out 25 pixels larger on each side (measured on Fedora 44 with GNOME: (-25,-25) 690x567 for a window drawn at (0,0) 640x517). The node subtracts what GTK declares in `_GTK_FRAME_EXTENTS`; a window framed by the desktop (KDE Plasma) keeps its rectangle. On Windows the same: since Vista a window's rectangle includes its invisible resize border, and a maximized window came out at (-9,-9), 18 pixels wider than the screen (measured at 125%); the node asks the desktop window manager what it draws (`DWMWA_EXTENDED_FRAME_BOUNDS`), and the fallback capture that composes the desktop window by window pastes only that part.

- A program `delphi_paserver remote-run` starts on Linux when PAServer runs outside the graphical session gets the session's X authorization, read from what the session gave the user's systemd manager (what `systemctl --user show-environment` shows). It was guessed with GNOME's file name, and on KDE Plasma, whose file is `xauth_*`, an FMX app died with "Authorization required" (exit 134): measured on Fedora 44 with a PAServer started without the session's environment, with the 1.27.1 launcher and with the new one. The desktop node takes the same for its window list, and its diagnosis no longer says that a Plasma session has no Xwayland authorization.
