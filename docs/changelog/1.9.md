# Changelog: the 1.9 line

The entries of the 1.9 line, moved here whole from [CHANGELOG.md](../../CHANGELOG.md): nothing was cut or reworded.

## [1.9.1] - 2026-10-02

A `ReadOnlyPaths` entry outside every root of its workspace is said at startup: the key that lets an agent read a folder outside its roots is `ReadOnlyRoots`.

### Added

- **The startup log warns about a `ReadOnlyPaths` entry that falls outside
  every root of its workspace.** `ReadOnlyPaths` marks as read-only the
  folders that are already INSIDE the roots - a `vendor/`, a submodule - and
  for a folder outside them its agents get nothing, neither reading nor
  protection. Measured 2026-10-02 on a second machine running this server:
  two workspaces declared `ReadOnlyPaths=L:\...` so that their agents could
  read the code of this project's machine without touching it, neither
  could (`GUARD-002`), and the startup said nothing. The key for that is
  `ReadOnlyRoots`. The entry is still loaded - it stays among the places no
  workspace may delete or purge - but the startup now says, for an entry of
  a `[Workspace.<name>]` and for one of `DELPHI_MCP_READONLY_PATHS`, the
  key, the entry, and the key that does open a folder for reading, as it is
  called there (`ReadOnlyRoots`, `DELPHI_MCP_READONLY_ROOTS`). Not for an
  entry inside one of the workspace's own references, nor for one that
  contains a root (it makes the whole root read-only); a relative entry is
  said only when it resolves outside (`..\shared`), once even if it does
  from several roots; a section with no token, which is ignored whole, says
  nothing more. Correction measured on 2026-10-04: protection compares the
  declared path and the real path with the same 8.3-aware location rule.
  An entry containing a root by its text protects it even if the root is a
  junction elsewhere. The previous claim that it protected nothing came
  from a TEMP path with an 8.3 component. Startup compares both forms on a
  local drive, and only text on a network drive, without waiting on a share. With no
  roots - the trusted local mode, which reads the whole machine - there is
  no outside, and nothing is said.

`test_letras_red` has fourteen more checks. The entry outside is loaded -
another workspace whose root contains it cannot delete it - and its agent
gets `GUARD-002` for it; an entry that contains the root makes it
read-only, including one that contains it by its text (the latter check
was corrected on 2026-10-04). The warning comes with its key and entry - a
whole drive with its backslash -, for the entry that leaves a root through
a junction, and once for a relative one that resolves to the same place
from two roots; nothing
for the entries inside (absolute, relative, in a reference of its own,
containing the root, in 8.3, and written by the real path of a root that
is a junction), nor for a section with no token; and the same for the
environment of the local mode, with its own key, with and without roots.
Twelve mutants of the warning, each built and run against that battery,
all twelve red: no warning at all, every entry taken as outside, a
warning with no roots, the workspace's own references not counted, the
comparison on the text instead of the real path, a whole drive without
its backslash, an entry containing a root taken as outside, one
containing a root only by its text taken as inside, the same entry said
once per root, a warning for a section with no token, the key of the
`.ini` named to the environment, and an absolute entry not loaded at all -
which the check of the delete catches: the folder was deleted.
A first version compared on the text alone, and its first review found
what that missed: an entry containing a root and an entry behind a
junction were a false warning or a missing one, the message said "cannot
even read" of a folder the library zone reads, it named the key of the
`.ini` to the environment, and an 8.3 name on a network drive could make
the startup wait on the share. The second review held that an entry
containing a root only by its text protects it, as the jail compares the
text too; measured, the write through that root goes through, and the
comparison stayed on the real path.

### Documentation

- QUICKSTART: the two read-only keys where a workspace is first written,
  with an example, and the symptom in its table of
  problems. README and `settings.example.ini`: what a `ReadOnlyPaths`
  entry outside the roots does and does not do, and `ReadOnlyRoots` as the
  key for "read our code, wherever it is, and touch nothing".
- README: **network shares are opt-in**, and why (published on 2026-10-01,
  between versions). A share becomes part of the Delphi environment only
  when the operator maps it to a drive letter on the RAD Studio machine and
  declares a place on it in a workspace; a share nobody mapped stays
  outside the boundary on purpose. Eight tools given a network path nobody
  declared, on a host that does not route, answer `GUARD-002` in 0.02 s or
  less: the refusal comes before the server goes to that host. One
  exception, kept by decision: with `LibraryZone=1`, a folder of the IDE's
  Library Path written as a network path is read like the rest of that
  zone (read in the code, not measured).

## [1.9.0] - 2026-10-01

A place is declared by a path with its drive letter; the server connects the network letters of its places for itself, and a root that is a whole drive works.

### Added

- **The server connects the network drive letters of its places at
  startup, and keeps trying.** A network drive letter belongs to the logon
  session that connected it, and a Windows Service does not see the ones of
  the user's desktop, even under the same account (measured 2026-10-01 with
  a program run by the service). A root on such a letter did not work
  there - a write under it answered "the drive cannot be found" - and the
  startup log said nothing: found on this project's own production
  service, the day a root on a letter of a NAS share was added to it. At
  startup, for each drive letter of a root, a reference or a vault - of
  every workspace that is not closed, and of the local launch mode - that
  the process does not see, the server now looks up the account's
  persistent mapping of that letter (`HKCU\Network\<letter>`,
  `RemotePath`: what Windows records for a drive mapped with "reconnect at
  sign-in"), connects the letter for its own session
  (`WNetAddConnection2`, no credentials passed, nothing written to the
  profile) and checks that each place declared on it is a folder that
  opens. A letter that is already a network drive for the process is only
  checked; one that Windows refuses to connect because something else
  connected it at the same moment is taken as connected. Each step is a
  note of the startup log; a letter with no persistent mapping, a
  connection Windows refuses (the note carries its error number) and a
  place that does not open are warnings. A letter that has a mapping and
  did not connect because the network or the share was not there - a
  service started before the network, a NAS that was off - is tried again
  every 30 s in the background, without repeating the warning, and the log
  says when it connects. Only those errors: one of credentials or of
  permission is said once and not retried, because insisting would be two
  failed logons a minute against the share. Nothing else changes: a
  place that cannot be reached stays declared, and nothing of this goes in
  `settings.ini`. The part that goes out to the network runs apart: the
  startup waits 15 s for it at most, then says so and goes on, and what
  the check finds afterwards goes to the log; with no network letter among
  the places no thread is started. The rule lives in `Lsp.NetDrives` and
  takes what it asks the machine as a parameter, so it is tested without
  drives.

  Measured on that production service, with the share's credentials being
  other than the account's: the log says the letter was not connected for
  the process, that it was connected to the share in 16 ms and that the
  root is reachable, and the smoke test's write under that root, which had
  failed, passed. Measured with a simulated machine only: a share that is
  down, the 15 s limit, the retry and the letter something else connects.
  Not measured: a connection Windows refuses, the tray mode started at
  sign-in before the network is up, and whether the rest of the startup -
  which walks the roots to clean its temporary folders - waits on a share
  that is down.

- **A root that is a whole drive (`Roots=N:\`) works.** The server keeps
  its places with their final backslash and took it off to compare them,
  to use them and to show them - in 104 places - and of `N:\` that left
  `N:`, which to Windows is not the root of the drive but its CURRENT
  folder. It went unnoticed while the server ran from another drive; with
  the server on the drive that is its root, the root became the folder it
  ran from and almost every path was refused as a link leading outside
  (`GUARD-001`). `delphi_workspace` showed such a root as `srvn:`, which
  sent back was `GUARD-021`: found on the production service with a root
  that was a whole NAS share. The final backslash is now taken off by two
  functions and by nobody else (`Lsp.NetDrives`: `SinBarraFinal`, to use or
  to show a path - the root of a drive keeps its backslash - and
  `PrefijoSinBarra`, for arithmetic on the text of a path), and the two
  functions every place comparison goes through (`RealPath`,
  `LongCanonical`) take a bare drive as its root. `delphi_workspace` and
  the refusals show such a root as `srvn:\`.

  Measured with `test_raiz_unidad`: test drives made with `subst` on
  temporary folders, the server running from the drive that is its root -
  a root, a reference and a vault that are whole drives; list, read,
  search, create, edit, move, delete, a project created and built there.
  31 of its 36 checks fail with the code of before and none now (18 of 30
  before the battery made its first call from another workspace, which is
  the fix of the drive letters below); one of them
  is static, that no other unit of the server calls the RTL's
  `ExcludeTrailingPathDelimiter`. Not measured there: git (to git a
  `subst` drive is the folder under it, `GIT-041` as for any `subst`
  letter since 1.8.2; the rule that reads git's answer for a network
  letter that is a whole root is in the unit tests) and what is particular
  to the root of a real volume.

### Changed

- **A place is declared by a path with its drive letter.** An entry of
  `Roots`, `ReadOnlyRoots`, `ReadOnlyPaths` or `VaultPath` - or of their
  `DELPHI_MCP_*` variables - that, once made absolute, is not `X:\...` is
  left out: a network path (`\\host\share\...`, `//host/share/...`), a
  device path (`\\?\UNC\...`, `\\.\UNC\...`, `\\?\GLOBALROOT\...`,
  `\\?\C:\...`). Nor is an entry with a wildcard, which was loaded as it
  was written and matched nothing, or one relative to the current folder
  of a drive (`N:folder`); a bare drive (`N:`) is its root - with the
  server on that drive it was loaded as the folder the server ran from.
  Nor one that starts with a single slash: to Windows `\vendor` is the
  root of the drive the process runs from, and `ReadOnlyPaths=\vendor`
  was loaded against that drive with no warning while the `vendor` of the
  workspace stayed writable (measured). Nor a relative entry of `Roots`,
  `ReadOnlyRoots` or `VaultPath`: it was loaded against the folder of the
  process, which for a service is System32 (in `ReadOnlyPaths` a relative
  entry is, as before, that folder of each root). A
  startup warning names the key and the entry. Until
  1.8.2 a root written as a network path was accepted. The agent sees
  drive letters as virtual units and the outbound mask is built on them; a
  place with no letter had no unit, and with the first entry above a
  letter of a share now works for a service as well. A workspace left with
  no root admits nobody, the same fail-closed as before. The library zone
  (the IDE's own paths) is not touched by this.

- **A protection that is not loaded closes, it does not open.** An entry
  of `ReadOnlyRoots`, `ReadOnlyPaths` or `VaultPath` that is not loaded -
  for the reason above, or because it does not parse (a wildcard, a
  character Windows does not allow in a path), which until now was dropped
  in silence - closes its workspace: its tokens get 401 and the warning
  says so. Those keys say what must not be written, and with the entry
  left out and nothing more, what it names could be. In the local launch
  mode the process admits nothing and says why (`GUARD-030`; the startup
  summary of the jail says CLOSED, `GUARD-031`, `delphi_workspace` says
  `closed`, and the roots and the vault of the environment are not loaded,
  so nothing walks them and `vault_read` has no vault; `delphi_projects`
  with no root answers the same `GUARD-030`, and the refusal comes before
  anything is looked up on disk - a file named with a final slash was
  answered "it is a file", and a network path was looked up before it
  was refused, 1.3 s with a host that does not exist); a workspace entered
  with its own token is not affected by the environment's lists.

### Fixed

- **A local client started with the token of a closed workspace is
  closed too.** `DELPHI_MCP_TOKEN` binds a stdio process to the jail of
  the workspace it belongs to. When that workspace was closed - no root
  that loads, a repeated key, a shared token - the binding skipped it and
  the process fell back to the trusted local mode, which with no
  `DELPHI_MCP_ROOTS` reads the whole machine (read-only). Read in the
  code, the mechanism was there for every cause of a closed workspace; a
  workspace whose roots are network paths, open until 1.8.2, would have
  met it on upgrading, and that is the case measured. Such a process now
  admits nothing (`GUARD-030`, naming the workspace).

- **A workspace's read-only token in `DELPHI_MCP_TOKEN` binds the local
  process to that workspace, read-only.** It bound nothing, and the
  process was left in the local mode - the whole machine, read-only, with
  no `DELPHI_MCP_ROOTS` - instead of in the jail its operator had given
  that token (measured). The same for the write token put in
  `DELPHI_MCP_READONLY_TOKEN`. As with a Bearer over HTTP, the secret says
  the workspace. And it binds the LOCAL client alone: a read-only token in
  the environment of a server made the whole process read-only, so over
  HTTP the write token of every workspace was refused too (it was already
  so for `DELPHI_MCP_READONLY_TOKEN`; measured).

- **Purging a file through a link that is in the trash no longer deletes
  the live file behind it.** A junction that is deleted goes to the trash
  as a link. `delphi_delete purge=true` of `<trash>\<the link>\file`
  passed for a copy in the trash by its text, and the file it deleted for
  good, with no copy, was the live one (measured). The purge now asks where
  what it is given really is; the link itself can still be purged.

- **`DELPHI_MCP_ROOTS` with text and nothing loaded refuses before the
  disk is looked at**, like the closed local mode: it is the same state,
  and its refusal came after the vault and the network path had been
  looked up. And it closes the local mode alone: a client that came in
  with the token of an open workspace - its jail is its own - was refused
  everything (`WS-004`), over stdio and over HTTP, which a server with
  `DELPHI_MCP_ROOTS` written as a network path would have met on
  upgrading (measured).

- **Each workspace is served with its own drive letters.** The letters
  the server shows as virtual units (`srvd:`) were worked out once per
  process, with the workspace of the FIRST call. A second workspace with
  its root on another letter saw that root as `srv0:\` and got "not a
  drive of this server" for its own `srvn:\...`, until the server was
  restarted with it calling first (noted in 1.8.2; measured now with two
  workspaces on two drives, in both orders). They are kept per workspace.

- **The startup does not wait for a root on a network drive to be
  walked, and leaves there what another machine may be using.** At
  startup the server empties every `__delphi-temp` under its roots, and
  finding them is walking the whole tree: 2.6 ms per folder measured on
  the production service with a root that is a share of a NAS (1.2 s
  with 580 folders, before it listened; it grows with the share). And the
  lock that says "this temporary folder belongs to a live server" is of
  ONE machine: a server on another machine, with a root on the same
  share, lost what it had in flight. For a root on a network drive that
  cleaning now runs apart from the startup and leaves whatever was
  created or written in the last hour - a file, or a folder with anything
  recent under it, whole; a line of the log says what it found and how
  long it took. Roots on local drives are cleaned as before.

- **`delphi_git diff`, `show` and `log`: the lines of content travel as
  they are on disk.** The outbound mask of drive letters rewrote the lines
  of a diff as if they were paths of the server: a `'\\host\x'` in a
  string literal came out `'\\srvhost\x'` and a `'Z:\x'`, `'srv0:\x'`
  (measured; seen reviewing a diff through the tool). The lines that
  start with `+`, `-` or a space - a line of a file, or of a commit
  message - are not touched; the others, which are git's and can name a
  path of the server, are masked as before.

- **A network path that opens a line inside a JSON answer is masked.**
  Inside JSON a line break is the two characters `\` and `n`, and the
  rule that masks the host of a network path looked at the character
  before it: after a line break it saw the letter `n` and let the path
  through with the name of the machine (noted in 1.8.2). And one written
  backslash followed by `n`, `r` or `t` - a folder of that one letter -
  is no longer read as a line break by the same question.

- **A file named with a final slash, outside the jail, is refused as
  outside.** `delphi_list root=<a file>\` answered that it was a file
  before the jail was asked, so any path of the machine could be probed
  for a file (measured). The jail goes first.

- **Purging the last copy of a trash folder leaves no empty folders.**
  `delphi_delete purge=true` of the only copy left `deleted`, the folder
  of the day and `__delphi-patch` itself in the root for good (seen on a
  NAS share after a smoke test). They are removed, from the bottom up, as
  long as they are empty.

- **`delphi_package` of the root of a drive with no `outfile` says what
  to do (`PKG-004`).** The default zip goes next to the folder, and a
  drive has nothing next to it: the name came out as `-deploy.zip` and
  the refusal was the one of a relative path.

- The folders of the IDE the server joins names to (`bin`, `PAServer`,
  the SDKs) work when RAD Studio or its SDK folder sits at the root of a
  drive (read in the code; not measured).

Twenty-five unit tests with a simulated machine, on the two functions of
the final backslash and on the cleaning with a cut-off
(`LspTests.LetrasDeRed`), and three on the mask after a line break of
JSON (`LspTests.Rutas`). `test_letras_red` measures the real startup -
which places it looks at, what the log says, the entries that are not
loaded and what they close, over HTTP and in the local mode - with
thirty-nine checks, two more when it is given a folder of a connected
network drive (`DELPHI_MCP_TEST_NETDIR`). `test_raiz_unidad` is the one
above, and `test_git_branches` has the four of the diff. Seventy-seven
mutants, seventy-five of them red in a unit test or in a check of those
batteries. The two that stay green: that the cleaning of a root on a
network drive goes apart (a battery has no network drive: the line it
writes in the log of an installed service is the measure), and that a
network path is refused in the closed local mode before it is looked up
(the refusal is the same either way; only the time tells them apart).
The unit tests of the startup no longer wait on the clock: the rule says
when its thread has ended, and the share that does not answer is a gate
the test opens. A13 of `test_alias83`, which measured
that a root declared by the UNC of a share was read, now measures that it
is not loaded while the share answers; its A14 (`\\srvhost\...` coming
back to the one declared UNC host) is gone with the UNC root, and that
return - still reachable through a folder of the library zone on a UNC -
is left with no check. Never run by a test: the three calls to Windows
that connect for real (the registry read, `WNetAddConnection2`, the
folder check); they were measured on the production service.

Known and left as it is: the places of a closed workspace are not loaded,
so they no longer protect themselves against ANOTHER workspace whose root
contains them; when a share does not answer, the process waits up to 15 s
while it loads its configuration - a service before it answers the
service manager, which gives it 30 s; the tray before it shows its icon.
A letter whose share was removed from a server that answers is retried
every 30 s for as long as the server lives: Windows gives the same error
(67) for that and for a host that is not there, which is the case the
retry exists for (measured).
