# Deep review — can you do all of your Delphi programming remotely with this server?

> **Note (2026-09-22)**: a snapshot of 0.56.0-beta (39 tools), kept as history.
> Since then: `delphi_test` exists since 0.58, `switch`/`merge`/`stash` since 0.57,
> `rename_symbol mode=apply` since 1.0.17, the runner was removed in 0.98 and phase 2 of the designer is parked.

**Date**: 2026-08-25 · **Version reviewed**: 0.56.0-beta · **Method**: measured against
production (39 tools, 34 core + 5 vault), reading the code, and a field test
with an agent that worked **only** through the MCP tools.

The question this document answers is not "does it have many tools?" but the only one
that matters for the project's goal: **can an agent with no Delphi, no access to the
disk and no shell do a programmer's whole job?**

---

## 1. A programmer's cycle, tool by tool

| Stage | Covered? | With | Gap |
|---|---|---|---|
| Discover the ground | **Yes** | `workspace`, `installs`, `projects`, `list`, `search`, `components` | — |
| Understand the code | **Yes** | `read` + the 8 LSP tools (`symbols`, `definition`, `hover`, `references`, `signature`, `completion`, `diagnostics`, `rename_symbol`) | 0-based vs 1-based positions; `completion` without a filter |
| Write | **Yes** | `edit`, `textedit`, `create`, `changeset`, `delete`, `move`, `config`, `styles`, `designer` | the designer does not write yet (phase 2) |
| Verify | **Yes** | `diagnostics` (without compiling), `build` (real MSBuild) | **no tests** (`delphi_test` does not exist) |
| Run | **Yes** | `run` (local, opt-in), `paserver remote-run` (target), `adb` (Android) | no stdin, no environment variables |
| Distribute | **Yes** | `package`, `fetch`, `upload`, `build target=Deploy` | large binaries go up only as base64 |
| Version | **Partial** | `git`: status, diff, log, show, branch, add, commit, init, config, clone, pull, fetch, push, tag | **no `checkout`/`switch`**, merge, stash, reset |
| Coordinate | **Yes** | `report` (agent→operator), `messages` (operator→agent) | — |
| Remember | **Yes** | 5 vault tools | — |

**Verdict**: the cycle is closed end to end. An agent can discover, read, understand
semantically, write with a safety net, compile, deploy to another machine, run there
and bring the binary back, without touching the disk or a shell. What was verified today
against the real target (GalateaFMX starting on Zorin from the MCP and returning its
output) is the proof that the last piece closes too.

There are **three real gaps** and several frictions. None of them invalidates the goal;
all of them are bounded and measurable.

---

## 2. Real gaps (ordered by what they cost)

### H1 — You cannot switch branches (`git checkout`/`switch`)
`delphi_git` can create branches (`branch`) but **not switch to them**, nor `merge`,
nor `stash`, nor `reset`. An agent working "the way a programmer does" (a branch per
task, commit, back to main) **cannot**: it can only commit on the branch someone
left it on.
*Impact*: high for real autonomous work; today it goes unnoticed because agents always
work on `main` of a sandbox.
*Careful*: `checkout <path>` **discards changes** — expose `switch`/`checkout -b`
(branches) and leave out the form that destroys files, or require a confirmation.

### H2 — There are no tests (`delphi_test`)
`build` says whether it compiles; nothing says whether it **works**. The loop that really
gives autonomy (edit → diagnostics → build → **tests** → commit) is broken at the
second-to-last step. Today an agent can build a test project and run it with
`run`/`remote-run`, but it has to parse the output by hand and cannot tell "the binary
failed" from "2 tests failed".
*Impact*: high. It is what separates "writes code that compiles" from "delivers code that
passes".

### H3 — Long operations: no progress, no cancellation
`build` of a large project, `get-sdk`, a 70 MB `package`: the agent calls and waits
in the dark until the timeout (600 s for build). There is no way to see progress or to cancel.
*Impact*: medium; it shows mostly in clients with a per-call time limit.

---

## 3. Measured frictions (cheap to fix)

1. **0-based vs 1-based positions**. `read`/`search` return 1-based lines; the 8
   LSP tools take 0-based. Chaining "search → navigate" fails the first time, every time.
   *Fix*: accept `line1`/`character1` as explicit aliases (the aliases of 0.46
   already solved the same problem with `query`/`pattern`/`filter`).
2. **`completion` without a filter**: it returns 50 of 4183 candidates with no way to narrow
   them by prefix, which is exactly how it is used (`Load…`). *Fix*: a `prefix` parameter.
3. **`run` without stdin or environment**: a program that reads from the console cannot be
   tested, and variables cannot be set. *Fix*: `stdin` and a bounded `env`.
4. **`upload` only as base64**: uploading a large binary costs model context. The
   way down (`/files` + sha256) is flawless; the way up has no equivalent.
   *Fix*: `POST /files` with a binary body.
5. **No common truncation vocabulary**: `search`, `list`, `components`, `completion`,
   `references` each cut in their own way. *Fix*: uniform `limit`/`offset`/`truncated`.

---

## 4. What is surprisingly good (do not touch)

- **The security doctrine holds up under audit**: an external agent attacked it
  (jail, auth, scope) and found no bypass; the two findings were surface-level and
  are now operator switches (`LibraryZone`, `RemoteRunProjects`).
- **Remote execution behind two locks in series** (`AllowRemoteRun` + a started runner),
  limited to the project's deployed binary: it is stricter than the IDE itself.
- **Anchor editing + transactions**: `changeset` closes the hole that was left
  (partial changes) and has already been used in the field for 16 edits in 2 files.
- **The report→fix→deploy loop**: from 0.46 to 0.56, *every* version came out of
  frictions reported by real agents. That is a method, not an anecdote.
- **Real semantics** (the official DelphiLSP) instead of grep: inheritance, overloads,
  active IFDEFs, cross-unit.

---

## 5. What I would do next, in this order

1. **`git switch`/`checkout -b`** (+ `merge --ff-only`, `stash`): cheap, and it unblocks
   working by branches. Without the destructive form of `checkout <path>`.
2. **`delphi_test`** (DUnitX): `discover`/`build`/`run` with a structured result
   (total/passed/failed/fixture/message). With its own `AllowTests` switch, not
   hanging from `AllowRun`.
3. **1-based aliases in the LSP tools** + `prefix` in `completion`: two parameters that
   remove the trap stepped on most often.
4. **Designer phase 2** (`set-property`, `bind-event`) on top of `changeset`.
5. **`rename_symbol` apply** on top of `changeset`, once the preview has been broken in.
6. Progress/cancellation and `POST /files`, if a case turns up that needs them.

---

## 6. Conclusion

**Yes, you can program remotely, and more so today than yesterday**: the whole cycle is
covered and tested against real machines (Windows compiling, Linux running, Android
deploying). What is missing is not power but **a programmer's craft**: working by
branches and knowing whether the tests pass. With H1 and H2 closed, an agent can do a whole
task —branch, change, tests, commit— without a human touching anything.
